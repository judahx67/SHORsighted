# What defeats SHORsighted

This file is a feature, not an apology. A detection tool without a published
failure list is asking to be trusted on vibes, and the whole argument for this
one is that it shows its working.

Everything below is **measured**, not guessed. The numbers come from
[`eval/report.md`](eval/report.md), regenerated by `python -m eval.run` against
the corpus in [`corpus/`](corpus/). Where a row says "we miss this", there is a
sample in `corpus/src/` that proves it.

## The honest summary

On a corpus of 104 binaries built from 26 sources:

| Detector | Precision | Recall (against what it should find) |
|---|---|---|
| imports | 1.000 (44/44) | 1.000 |
| constants | 1.000 (58/58) | 1.000 |
| heuristics | 1.000 (16/16) | 0.800 |

Overall recall **including the defeat set is 0.797**. The gap between those
numbers is this document.

And the number that matters most for reading the ones above: **the corpus is
built by us, not collected from the wild.** Ground truth is exact, which is
worth a great deal, and the sample distribution is ours, which is worth
watching. These are optimistic.

## 1. Cryptography with no constants and no imports

**Sample:** `defeat_runtime_sbox.c` · **Result:** found nothing. Ground truth: AES.

An implementation that computes its tables at startup — the AES S-box from the
multiplicative inverse in GF(2^8), for instance — never stores them. There is no
byte pattern to match and no import to read. The binary contains the
*derivation*, not the table.

This is the hard ceiling of static byte analysis, and no number of extra
signatures moves it. Getting past it needs a disassembly-based detector that
recognises the *shape* of the computation, which is a much larger tool
(roadmap v0.3, and it would bring a Capstone dependency with it).

## 2. One XOR of obfuscation

**Sample:** `defeat_masked_sbox.c` · **Result:** found nothing. Ground truth: AES.

A table stored XOR-masked with a single byte and unmasked at startup defeats
every byte pattern this project ships. It is the cheapest possible evasion:
three lines of C.

Worth stating plainly because it bounds what this tool is *for*. SHORsighted is
an inventory tool for software that is not trying to hide — your vendor's
installer, your own build output, the DLLs under Program Files. It is not an
anti-evasion tool, and against something actively hiding it will lose.

Brute-forcing single-byte masks is possible (256 passes) but multiplies scan
cost by 256 to catch a case a determined adversary defeats again with a two-byte
key. Not planned.

## 3. Constants the optimiser deleted

**Sample:** `defeat_folded_sigma.c` · **Result:** found at `-O0`, missed at
`-O2`. Ground truth: ChaCha20.

No evasion at all — just optimisation. ChaCha20's sigma is sixteen bytes
(`expand 32-byte k`), and at `-O2` the compiler turns the copy into four
immediate operands. The constant is not in the file any more.

Short constants are fragile in a way a 256-byte S-box is not. This is the
practical reason the constant detector's precision is high while its coverage is
uneven: algorithms with big distinctive tables (AES, SHA-2, SHA-3, MD5) are
reliable, and algorithms whose signature is a handful of bytes are a coin flip
against the optimiser.

## 4. Big integers in the wrong limb order

**Sample:** `defeat_p256_limbs.c` · **Result:** found nothing. Ground truth: ECC/P-256.

Curve parameters ship in our signatures as octet strings, which is how a library
that keeps field elements as byte arrays stores them. A bignum library that
works in machine words stores the same value as little-endian 64-bit limbs — a
different byte sequence entirely. `static_p256.c` (octet strings) is found;
`defeat_p256_limbs.c` (limbs) is not.

**This one is fixable and should be fixed.** Word tables already expand into
both contiguous layouts at load time; curve constants do not, because they are
raw `pattern` entries rather than `words` entries. Teaching the loader to expand
curve parameters into limb layouts is a bounded change to
`signatures/schema.py`, and it is the highest-value item on this page.

## 5. Algorithm names the legacy CryptoAPI never writes down

**Samples:** `capi_md5.c`, `capi_rc4.c` · **Result:** "CryptoAPI" and nothing
more. Ground truth: CryptoAPI + MD5, CryptoAPI + RC4 + SHA-1.

CNG takes its algorithm as a wide string (`L"AES"`), which survives into
`.rdata` and is what the import detector's corroboration rule reads. The older
CryptoAPI takes an integer: `CALG_MD5` is `0x8003`, compiled straight into an
instruction operand. There is no string to find.

So on legacy CryptoAPI binaries the tool can say "this does cryptography" and
genuinely cannot say which. It says exactly that, and does not guess.

## 6. High-entropy detection, switched off

**Samples:** `embedded_raw_key.c` (a real key), `negative_entropy_blob.c` (not a
key), and every other binary in the corpus.

The entropy heuristic (FR-8) measured **4 true positives against 100 false
positives** — precision 0.038. It fired on all 104 binaries, including every
negative sample and the plain hello-world control.

It **ships disabled**. Turn it on with `enabled = true` under `[entropy]` in
`signatures/data/material.toml` if you would rather triage the noise than miss a
bare key.

The interesting part is *what* the false positives were. The module's own
docstring predicted compressed data. The corpus says otherwise: the dominant
source is IEEE-754 double-precision constant tables in the C math library —
`pow`, `exp`, and `log` coefficients, which are near-uniform at 32-byte
granularity and present in essentially every compiled binary.

That suggests a fix rather than a funeral. A run of doubles has a very
recognisable shape (every eighth byte is a small exponent field), and a
structural suppressor along those lines would likely recover most of the lost
precision. Not attempted in v0.1 because it is new detector logic rather than
new data, and shipping it uncalibrated would repeat the mistake this section
exists to record.

Note also that the recall figure rests on **one sample**. A random 32-byte key
averages about 30 distinct bytes and the threshold is 30, so recall sits right on
a cliff edge; read 4/4 as "it can work", not as a rate.

## 7. Packed and .NET binaries

Both are **reported as such** rather than as clean — `degraded-packed` and
`unsupported-managed` in the CBOM — and FR-13 means a scan of one of these that
finds nothing has found nothing *about that file*.

Neither is measured here. Packing needs a packer in the corpus build, which
would mean shipping UPX in CI; .NET needs a managed toolchain. Both are on the
roadmap, and both are currently unit-tested for the status they set rather than
for their effect on detection rate.

## 8. What the corpus does not contain at all

- **Real static OpenSSL, mbedTLS, or libsodium.** The static arm of the corpus
  is reference implementations compiled in. They exercise the same tables, but
  not the same code layout, inlining, or the vectorised variants a real library
  ships — an AES-NI build of OpenSSL has no S-box in it at all. The import
  signatures for those libraries are shipped **untested against a real build**,
  which is why `import-specific` confidence is borrowed from `import-generic`
  rather than measured.
- **Post-quantum algorithms.** No ML-KEM or ML-DSA constants ship, and nothing
  in the corpus contains them. For a tool whose name is a Shor joke this is the
  most embarrassing gap on the page, and it is first in line after the curve
  limb layouts.
- **DES and 3DES constant tables.** See `tools/derive_constants.py` for why the
  permutation tables were judged too weak a signal to ship without measurement.
- **Anything much larger than 800 KB.** Throughput was benchmarked separately
  (277 MB/s against NFR-1's 25 MB/s requirement); detection *quality* on large
  real-world binaries is not measured.

## 9. What a finding does and does not mean

Not a defeat, but the most common misreading, so it belongs here.

A finding means **evidence of presence**. It does not mean the code runs, that
the algorithm is reachable, or that it is used for anything security-relevant. A
statically linked library brings its whole table section along whether or not one
line of it is ever called.

And no findings means **none detected**, never "no cryptography present". Every
section on this page is a way for that sentence to be true and useless at the
same time.
