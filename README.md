> *Your binaries are Shor-sighted.*

A CBOM scanner for **compiled Windows PE binaries**. It reads EXE/DLL/SYS files as bytes, detects evidence of
cryptographic algorithms and material, and emits a **CycloneDX 1.6** Cryptographic Bill of Materials.

Existing CBOM tooling reads source code. A great deal of real-world cryptography ships as statically linked
OpenSSL inside software nobody has the source to — invisible to every source-level scanner. That gap is the
point of this tool.

## The numbers

Measured on a corpus of **104 binaries built from 26 sources** (`corpus/`), regenerated by
`python -m eval.run` into [`eval/report.md`](eval/report.md):

| Detector | Precision | Recall |
|---|---|---|
| **imports** — dynamically linked crypto (CNG, CryptoAPI, OpenSSL, mbedTLS, libsodium) | **1.000** (44/44) | 1.000 |
| **constants** — statically linked crypto, found by its tables | **1.000** (58/58) | 1.000 |
| **heuristics** — embedded certificates and key material | **1.000** (16/16) | 0.800 |

Overall recall **including the samples designed to defeat it: 0.797**. That gap is
[`LIMITATIONS.md`](LIMITATIONS.md), and reading it is not optional — a detection tool without a published
failure list is asking to be trusted on vibes.

Two caveats stated here rather than in a footnote:

- **The corpus is built by us, not collected from the wild.** Ground truth is exact by construction, which is
  worth a lot; the sample distribution is ours, which means these numbers are optimistic.
- **Confidence values are Wilson lower bounds, not raw ratios.** Several classes scored a clean 1.000 and none
  of them ship at 1.00, because 20/20 on a corpus this size does not support that claim.

Along the way the corpus found something worth repeating: **Zig's runtime puts ChaCha20 into every x86\_64
debug build**, which none of the sample programs asked for. The tool reports it, correctly. That is the case
for binary-level CBOMs in one line — your source does not know what your toolchain linked in.

## Status: MVP, slice 10 of 12 🌱

```console
$ shorsighted app.exe                       # CycloneDX 1.6 JSON (the contract)
$ shorsighted app.exe --format text         # summary table, no stability guarantee
$ shorsighted "C:\Program Files\Vendor"     # whole install tree
$ shorsighted app.exe --min-confidence 0.9  # high-precision findings only
$ shorsighted app.exe --reproducible -o bom.json
```

All three detectors work. Point it at a file or a whole install tree and it emits a CycloneDX 1.6 CBOM naming
what it found, with evidence, offsets, and NIST quantum levels. Findings that two detectors agree on are merged
into one asset with combined evidence. Packed binaries and .NET assemblies are flagged as such rather than
reported as clean. Every document the test suite produces is validated against the official CycloneDX 1.6
schema in CI.

**What it cannot do:** see [`LIMITATIONS.md`](LIMITATIONS.md) — every entry there has a corpus sample proving
it. The short version: cryptography whose tables are computed or masked at startup, constants small enough for
`-O2` to fold away, big integers stored in machine-word limbs, and algorithm names the legacy CryptoAPI passes
as integers. The high-entropy heuristic measured 0.038 precision and **ships disabled**.

Requirements, design, and the build order live outside the repo. What ships here is the code, the corpus, the
evaluation, and [`LIMITATIONS.md`](LIMITATIONS.md).

## What it promises

- Evidence, not vibes — every finding carries its detector, signature id, and file offset, so you can check it.
- **Honest absence.** No findings means "none detected", with caveats attached (packed? managed? errored?).
  Never "no cryptography present".
- Published per-detector precision and recall on a labelled corpus, plus a candid list of what defeats it.
- It never executes, emulates, or modifies what it scans, and it never lifts key material into the output.

## Development

```console
$ pip install -e ".[dev]"
$ pytest --cov
$ ruff check . && ruff format --check . && mypy && lint-imports
```

Rebuilding the corpus needs [Zig](https://ziglang.org/download/) and nothing else:

```console
$ python -m corpus.build
$ python -m eval.run --print
$ python -m eval.run --check     # fails if confidence.toml has drifted
```

Detection knowledge lives in `shorsighted/signatures/data/*.toml`, never in Python. A byte pattern inside a
`.py` file is a bug. See [`corpus/README.md`](corpus/README.md) for how to add a sample.
